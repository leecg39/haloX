2026-10-23. S02/S03의 저장 데이터·화면을 연결했다. 전체 메뉴 작업은 [작업표](full-crud-tasks.md)를 따르며 아직 완료되지 않았다.

## 워크스페이스 설정

`/app/settings?tab=workspace`는 현재 선택한 워크스페이스의 이름·브랜드 이름·기본 도메인·슬러그·설명을 조회하고 소유자/관리자가 수정한다. `/app/workspaces`와 같은 `workspaces` 레코드를 사용하며 저장 후 목록·공통 헤더에도 반영한다. 생성·선택·삭제는 기존 워크스페이스 관리 화면으로 연결한다.

이름/브랜드 이름 100자, 설명 2,000자, 도메인 253자, 슬러그 100자 이내다. 도메인은 URL 경로 없이 `example.com` 형식으로 저장한다. 기존 시드의 브랜드 문자열은 변경하지 않는 한 유지하며 새 입력에는 도메인 검증을 적용한다. 슬러그는 문자·숫자·하이픈·밑줄을 허용하고 대소문자를 구분하지 않는 유일성을 검사한다. `expected_revision`이 다르면 409로 거절한다. 기존 REST에서 수정해도 버전이 증가한다. 관련 없는 `settings` 값은 프로필 저장으로 덮어쓰지 않는다.

진단 대상·URL·최대 페이지/깊이·포함/제외 경로를 등록·조회·수정·삭제한다. 별도 설정 사본을 만들지 않고 사이트 진단의 `site_audit_targets`와 `AuditTargetForm`을 공유한다. 사이트 진단 메뉴에서 같은 ID와 변경 값을 확인할 수 있으며 실행한 결과에는 당시 범위가 남는다. 실행 중 대상 삭제는 기존 진단 규칙대로 거절한다. 외부 수집은 저장만으로 시작하지 않는다.

2026-10-24 사용자 지정 robots/sitemap/llms 정책 파일 주소·초기화, 새 진단의 설정/파일 근거 보존, 기존 진단의 현재 사이트맵 통계 보완·진행/취소·이력 CRUD를 구현했다. [정책 파일 구현과 검증](site-policy-crud.md)을 참고한다. 원본 화면의 계정 탈퇴·30일 복원은 작업표 S13으로 남아 있다.

## 멤버와 초대

`/app/settings?tab=members`는 실제 멤버 목록·검색·역할 변경·제거, 초대 생성·목록/상태 필터·역할 수정·링크 재발급·취소·종료된 기록 삭제를 제공한다. `GET /api/v1/workspace-management?workspace_id=...`는 계정/역할·워크스페이스·멤버·초대·진단 대상을 한 스냅샷에서 읽는다. 모든 응답은 캐시하지 않는다.

`POST /api/v1/workspace-management` 명령:

- `workspace-update`: 워크스페이스 정보 수정.
- `invite-create`, `invite-update`, `invite-rotate`, `invite-cancel`, `invite-delete`: 초대 관리.
- `member-update`, `member-delete`: 역할 변경·제거.
- `invite-preview`, `invite-accept`: 받은 링크의 내용 확인·수락. 아직 대상 워크스페이스에 속하지 않아도 유효한 로그인 계정과 초대 링크를 함께 검증한다.

기존 `workspace-invite` 함수도 같은 생성 함수를 사용한다. 이메일을 소문자로 정규화하고 이미 참여한 멤버·동일한 대기 초대의 중복 생성을 막는다. 유효한 대기 초대는 워크스페이스당 최대 100개다. 중복 요청은 기존 초대만 반환하고 비밀 링크를 다시 보여 주지 않는다. 링크를 잃어버린 경우 명시적으로 재발급한다.

소유자는 관리자를 지정·변경·제거할 수 있고, 관리자는 일반 멤버를 초대·관리한다. 일반 멤버는 초대 내역을 조회하거나 멤버/설정을 관리할 수 없다. 소유자 멤버십은 변경·제거할 수 없으며 계정·워크스페이스 소유자 관계와 일치해야 한다. 동일 계정의 중복 멤버십과 없는 계정 추가를 거절한다. REST에서도 관리자 승격 우회와 초대 상태 직접 변경을 막는다. 멤버 이름은 계정 프로필의 현재 값을 표시한다.

현재 역할은 `owner`, `admin`, `member`, `viewer`다. 메뉴별 범위와 읽기 전용 역할의 서버 집행은 아래 S03 후속 항목을 참고한다.

## 초대 링크와 수락

생성/역할 수정/재발급 시 32바이트 암호학적 난수 링크를 한 번 반환한다. 원문은 DB에 저장하지 않고 비공개 `workspace_invitation_tokens`에 SHA-256 해시·초대 ID·워크스페이스/소유자 ID만 저장한다. 일반 조회/REST에는 토큰 원문이나 해시를 반환하지 않는다. 링크는 `/app/invite#token=...` 형태로 토큰이 HTTP URL의 경로·쿼리에 포함되지 않게 한다. 클라이언트의 레코드 localStorage에도 저장하지 않는다.

**이메일 자동 발송은 없다.** 화면에서 링크를 복사해 초대한 사람에게 직접 전달한다. 초대받은 이메일 계정으로 로그인하고 링크를 제시해야만 내용을 확인/수락할 수 있다. 이메일 계정만 일치하거나 초대 ID만 아는 것으로는 수락할 수 없다. 로그인/가입은 새 탭으로 열고 원래 초대 탭으로 돌아와 확인한다.

7일 만료, 역할 변경/재발급 시 이전 링크 무효화, 취소/수락 시 토큰 삭제를 적용한다. 잘못된 역할이 담긴 이전 초대는 수락할 수 없다. 멤버 추가·초대 수락 상태·토큰 소비는 같은 SQLite 트랜잭션이며 동시 수락은 한 건만 성공한다. 수락한 멤버를 제거해도 사용한 링크로 재참여할 수 없다. 멤버 제거 후 다음 API 요청부터 워크스페이스 접근이 차단되고 업무 데이터는 유지한다. 이전에 인증한 실행 중 요청을 소급 취소하지는 않는다. 수락한 초대 기록 삭제는 멤버를 제거하지 않는다. 워크스페이스 삭제 시 비공개 초대 해시도 정리한다.

## S03 후속: 뷰어·메뉴 권한 (2026-10-23)

`viewer` 역할과 `allowed_sections`를 멤버/초대에 저장한다. 초대 및 역할 변경 화면에서 대시보드(`dashboard`), 분석(`analysis`), 전략(`strategy`), 실행(`execution`), 모니터링(`monitoring`), 기타(`other`)를 선택한다. 기타에는 자료실·페르소나·Raw 데이터·워크스페이스 설정이 속한다. 내 프로필·복구·추천·피드백·워크스페이스 생성/선택은 계정 기능으로 유지한다. 소유자는 항상 전체 권한이며, 기존의 범위 미지정 멤버십은 전체 권한으로 호환한다. 빈 배열을 전체로 해석하는 기존 API 규약은 유지하되 화면에서는 하나 이상 선택해야 저장할 수 있다.

관리자는 자신에게 허용된 메뉴 범위 안의 일반 멤버만 관리할 수 있다. 본인보다 넓은 범위의 기존 멤버·초대를 변경/삭제하거나 넓은 범위를 새로 부여할 수 없다. 관리자 지정·관리 및 소유자 보호 규칙은 그대로 적용한다. 메뉴 범위 변경도 초대 링크를 교체하며, 수락 시 서버에 저장된 역할과 범위를 복사한다.

서버는 세션 토큰의 오래된 역할 대신 매 요청의 현재 멤버십을 사용한다. 공통 테이블 읽기에서 접근 불가 자료와 카운트를 제외하며 가입한 워크스페이스에서 허용되지 않은 메뉴의 명시적인 `workspace_id=eq...` REST 요청에는 403을 반환한다. 미가입/삭제된 워크스페이스의 REST 조회는 기존의 빈 결과 규약을 유지한다. ID만 지정한 수정/삭제와 워크스페이스를 생략한 생성도 저장 계층에서 검사한다. REST·RPC·`rpc-cache`·함수·집계·원본 파일 업로드/다운로드·리포트/내보내기 파일·OpenAI/WordPress 실행 경로를 검사한다. `rpc-cache`는 권한 오류를 성공 응답으로 바꾸지 않는다. 뷰어는 허용된 메뉴를 읽되 수정·삭제·실행·업로드·다운로드할 수 없다. 이미 읽은 자료의 복사 자체를 막는 DRM은 아니다.

다른 메뉴 자료를 참조하는 신규 집계/선택 목록은 허용된 원본만 사용한다. 연결된 메뉴의 쓰기도 필요한 작업(예: 기회 후보를 키워드로 채택, Raw 데이터 가져오기)은 목적 테이블 권한이 없으면 실패하며 SQLite 트랜잭션으로 롤백한다. 이미 생성한 콘텐츠의 참조 스냅샷·리포트·내보내기 파일은 각각 해당 문서가 속한 메뉴의 자료로 취급한다. 일부 자료만 표시할 수 있다는 안내를 화면에 표시한다. 사용량 원장 및 서버 이벤트 기록, 소유자 자격의 예약 실행은 서버 내부 작업이다.

클라이언트는 로그인/경로 이동/창 재활성화 시 서버 권한을 다시 읽는다. 사이드바·검색·모바일 메뉴는 허용된 경로만 제공하고 직접 URL 접근에는 권한 안내 화면을 표시한다. 뷰어에게 읽기 전용 안내를 제공하고 공통 편집 폼의 필드/저장 버튼을 비활성화한다. 직접 실행 버튼과 파일 API도 서버에서 거절하며 CSV 생성은 현재 권한을 재확인한다. 프로필/계정 기능의 폼은 영향을 받지 않는다.

API 키를 통한 우회를 막기 위해 발급·수정은 전체 메뉴 권한을 가진 관리자만 허용한다. 신규 키에는 서버가 발급자를 기록하고, 발급자가 제거되거나 관리자/전체 범위를 잃으면 기존 키도 인증되지 않는다. 발급자 정보가 없는 이전 키는 워크스페이스 소유자의 자격증명으로 취급한다. 이후 S11에서 API 키 자체의 세부 scope CRUD를 구현했다. [API 키 구현](api-keys-crud.md)을 참고한다.

검증: 새 단위 8개는 역할/메뉴 조합·ID 기반 우회·RPC 오류·초대 범위·관리자 범위 상승 방지·다운로드·자기 프로필·저장 상태 복원·키 발급자 권한 회수·숨겨진 멤버 ID의 직접 수정/삭제 차단을 확인한다. 새 E2E 3개는 뷰어 검색/저장 금지→같은 세션 승격, 메뉴/직접 URL/REST/HEAD/RPC/외부 서비스 차단, 화면에서 범위를 선택한 뷰어 초대 수락을 확인한다. 첫 실행의 테스트 선택자와 잘못된 Raw 종류(`serp`)를 실제 계약(`seo`)에 맞게 고쳤다. 기존 RPC 미지원 오류 문구와 삭제된 워크스페이스 REST 조회의 빈 결과 규약도 유지하여 기존 계약을 보존했다.

Ego Lite의 별도 3110 서버·임시 DB에서 멤버 범위 편집/저장, 다른 계정으로 뷰어 로그인, 검색·읽기 전용 폼, 직접 접근 거부를 확인했다. 동일 DB 서버 재시작 후 뷰어 역할과 분석 범위가 유지됐다. 390×600에서 가로 너비 390px, 실제 본문 스크롤 574px를 확인했으며 1428×747에서도 가로 넘침이 없었다. TaskSpace 50을 종료하고 임시 서버·DB·자격증명 파일을 정리했다. 실제 SMS·OpenAI·이메일 호출은 없었다.
