# 공개 사이트 콘텐츠·문의 CRUD 구현 및 검증

기준일: 2026-10-24

## 범위

공개 캡처 195개 경로를 콘텐츠 카탈로그로 등록하고, 서비스 운영자가 `/app/site-content`에서 페이지·글·분류·번역·문의 접수함을 관리하도록 구현했다. 저장 모델은 공개 REST 테이블에서 분리된 `site_pages`, `site_posts`, `site_taxonomies`, `site_translations`, `contact_requests`이며 SQLite 스냅샷 트랜잭션에 영속된다.

블로그 글은 `blog`, 용어집은 `glossary`, 변경 소식은 `update`, 나머지는 `page` subtype으로 분류한다. 경로는 `/ko` 또는 `/en`으로 시작하는 소문자 slug만 허용하고, 현재 초안 경로와 기존 게시 경로 전체에서 유일해야 한다. 분류 slug는 로케일 안에서 유일하다.

## 게시 모델

- 작성·수정 내용은 초안 행에 저장한다. `published_snapshot`만 익명 공개 페이지와 메타데이터에 사용한다.
- 편집 중 경로와 본문을 바꿔도 기존 게시 경로와 게시 본문은 재게시 전까지 유지된다.
- 캡처 페이지를 처음 편집할 때도 재게시 전에는 캡처 원본을 계속 표시한다.
- 신규 경로는 게시 전에는 404이며, 게시하면 로케일별 공개 셸 안에서 관리 본문을 표시한다.
- 운영자 화면은 초안 미리보기, 공개 보기, 수정, 게시, 삭제를 제공한다. 원문을 삭제하면 연결 번역도 함께 삭제 상태가 된다.
- 관리 본문은 HTML로 주입하지 않고 텍스트 기반 Markdown 문단·제목으로 렌더링한다.

서비스 운영자는 시드 계정 `admin@halox.local`의 고정 서비스 역할로 판별한다. 일반 워크스페이스 소유자나 관리자는 콘텐츠 관리 API를 사용할 수 없다. 모든 관리 쓰기는 revision을 요구하며 오래된 화면의 갱신은 409로 거절한다. 비공개 콘텐츠 모델은 `/api/v1/rest/*`에서 조회·수정할 수 없다.

## 문의 접수

한국어·영어 `/contact-sales` 캡처 양식을 `/api/v1/contact`에 연결했다. 문의 종류, 이름, 이메일, 회사, 업종, 규모, 전화번호, 본문, 로케일, 출처 경로를 저장한다.

- 개인정보 수집 동의를 서버에서 다시 확인한다.
- honeypot 입력은 저장 없이 성공으로 처리한다.
- IP는 원문 대신 SHA-256 해시만 저장한다.
- 같은 이메일은 한 시간에 3건으로 제한하고, 같은 이메일·본문의 5분 내 재전송은 한 건으로 합친다.
- 운영자는 문의 목록 조회, 상태(`new`, `contacted`, `closed`)·메모 수정, 삭제를 수행한다.
- 프로세스 IP 제한과 영속 이메일 제한을 함께 적용한다.

문의 접수 자체는 외부 알림을 보내지 않는다. 기존 개인 알림 기능은 사용자가 선택한 SMTP 이메일과 SOLAPI 문자를 사용하며, 자세한 설정은 [알림 구현 문서](notifications-crud.md)에 기록되어 있다.

## 주요 파일

- `src/data/site-content-catalog.json`: 캡처 공개 경로 195개의 초기 카탈로그
- `src/lib/backend/site-content-service.ts`: 권한, 검증, 게시 스냅샷, 관계 삭제, 문의 제한
- `src/app/api/v1/site-content/route.ts`: 공개 조회와 운영자 CRUD API
- `src/app/api/v1/contact/route.ts`: 익명 문의 접수와 운영자 상태 명령
- `src/components/live/SiteContentPage.tsx`: 운영자 콘텐츠·분류·번역·문의 화면
- `src/components/PublicManagedContent.tsx`: 공개 관리 본문 렌더러
- `src/lib/backend/site-content.test.ts`: 서비스 계층 회귀 테스트
- `e2e/site-content.spec.ts`: 게시 버전과 실제 문의 양식의 브라우저 검증

## 검증 증거

- 공개 콘텐츠 서비스 단위 테스트: 5/5
- 전체 단위 테스트: 346/346
- 백엔드 계약 검사: 22/22, RPC 36개, 테이블 59개
- 전용 E2E: 페이지 생성·게시·초안 격리·재게시·삭제, 익명 문의 접수·상태 수정·삭제, 비운영자 403 통과
- 전체 E2E: 112/112
- 경로 검증: 363개에서 누락·실패·중복·위험 URL·자산 누락 0개
- `npm run typecheck`, `npm run build` 통과

전체 E2E 첫 실행에서 기존 사이트 정책 시나리오의 SQLite 스냅샷 읽기가 `BUSY_RECOVERY`로 한 번 실패했다. 쓰기 잠금과 같이 읽기 스냅샷도 도메인 작업을 시작하기 전에 `BUSY/LOCKED` 코드를 비동기로 재시도하도록 저장소를 수정하고 결정적 잠금 테스트를 추가했다. 해당 시나리오 재검사와 전체 E2E 재실행이 통과했다.
